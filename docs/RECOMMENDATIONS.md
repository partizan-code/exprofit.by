# Рекомендации по сопровождению

Предложения подготовлены по локальной реализации и официальной документации **26 ноября 2026 года**. Это варианты дальнейшей работы: workflows, ресурсы, HTML, SEO и настройки хостинга в рамках документационной задачи не изменялись.

## GitHub Actions

Сейчас `.github/workflows` в репозитории нет. Разумный первый шаг — CI для pull request и push без публикации сайта:

- Выбрать поддерживаемую версию Node.js, совместимую с `engines.node >=22`, и зафиксировать её для CI. Начать с одного Linux runner; Windows/macOS добавлять при необходимости проверки платформенных различий.
- Запускать существующие `npm ci --ignore-scripts`, `npm test`, `node --check script.js` и `npm run build:css`; затем проверять отсутствие неожиданного diff в `exprofit.css`. Для сравнения результата сборки использовать одинаковую среду.
- Проверять локальные Markdown-ссылки. Изолированные браузерные проверки вводить отдельным шагом с запретом внешней сети до открытия страницы.
- Ограничить `GITHUB_TOKEN` правом `contents: read`, закрепить используемые actions полными commit SHA. Не добавлять credentials хостинга, реальные аналитические вызовы или deploy; такой CI не нуждается в production-секретах.

Это рекомендация для проекта, основанная на [руководстве GitHub по Node.js CI](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs) и [правилах безопасного использования Actions](https://docs.github.com/en/actions/reference/security/secure-use). Автоматическую публикацию следует рассматривать как отдельную задачу с явным разрешением владельца.

## Версионирование ресурсов

Сейчас CSS и JavaScript имеют постоянные имена `exprofit.css` и `script.js`; автоматического обновления URL нет. История наблюдавшегося кеширования и текущий порядок поставки сохранены в [DEPLOYMENT.md](DEPLOYMENT.md#кеширование).

Для небольшой ручной поставки можно начать с версии в URL ресурса, меняемой вместе с содержимым. При росте автоматизации рассмотреть имена с хешем содержимого: это потребует согласованного изменения сборки, ссылок HTML и состава поставки. Такие варианты URL описаны в [документации MDN по HTTP-кешированию](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching).

После выяснения настроек хостинга определить политику кеша отдельно для HTML и версионированных ресурсов. Новые ресурсы загружать перед HTML; старые сохранять для кешированных страниц и отката. Точные заголовки и сроки хранения выбирать по фактическому поведению сервера; в этой задаче оно не проверялось.

## SEO и представление ссылок

Уже реализованы `title`, `description`, canonical, текстовые Open Graph metadata, подтверждение Яндекса, `robots.txt` и sitemap с главной страницей. Основной HTML не содержит `noindex`. Дальнейшие шаги:

- Подготовить согласованное изображение для `og:image`, затем проверить карточку ссылки. Изображение входит в базовые свойства [Open Graph protocol](https://ogp.me/); сейчас в HTML его нет.
- Решить, нужна ли JSON-LD-разметка личности и сайта; включать только подтверждённые данные, соответствующие видимому содержанию. Разметка должна следовать [рекомендациям Google по structured data](https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data) и не означает гарантированного расширенного результата.
- Сохранять согласованность canonical, `og:url`, `robots.txt` и sitemap при смене домена. Обновлять `lastmod` по существенному изменению страницы, а не по каждому изменению документации. Google не использует `priority` и `changefreq` как сигналы sitemap: [требования к sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).
- После отдельно разрешённой публикации проверить ответы хостинга, HTTPS, редиректы и фактическую индексацию через инструменты владельца. Наличие метаданных в локальных файлах не подтверждает эти результаты.
